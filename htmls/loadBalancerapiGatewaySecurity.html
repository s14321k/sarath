Chapter One

Cloud Load
Balancing

GCP's Load Balancer distributes incoming traffic across multiple backend instances, ensuring high availability, fault tolerance, and horizontal scalability. It operates at both Layer 4 (TCP/UDP) and Layer 7 (HTTP/HTTPS).

🌐
Global vs Regional LB
GCP's Global Load Balancer uses Google's private backbone network to route traffic to the nearest healthy backend anywhere in the world. Regional LBs stay within a single GCP region and are cheaper for intra-region workloads.
Global → Anycast IP · Premium Tier
📐
L4 vs L7 Load Balancing
Layer 4 (Network LB) operates on TCP/UDP packets — it's fast but blind to content. Layer 7 (HTTP/S LB) understands HTTP — it can route by URL path, headers, cookies, and do SSL termination, content-based routing, and more.
L4 → TCP/UDP passthrough · L7 → HTTP routing
❤️
Health Checks
GCP LB continuously probes backend instances via HTTP, HTTPS, HTTP/2, TCP, or gRPC health checks. If an instance fails the threshold, it's removed from rotation automatically and traffic is redistributed.
checkIntervalSec: 5 · unhealthyThreshold: 2
📌
Session Affinity
Also called "sticky sessions." Ensures requests from the same client always hit the same backend instance, useful for stateful applications. GCP supports Client IP, HTTP cookie, and generated cookie affinity modes.
sessionAffinity: GENERATED_COOKIE
🔄
Backend Services & NEGs
Backend Services define how the LB connects to backends. Network Endpoint Groups (NEGs) let you target individual containers (GKE pods), VMs, serverless endpoints (Cloud Run), or on-prem via hybrid NEGs.
NEG types: GCE_VM · SERVERLESS · HYBRID_CONNECTIVITY
⚡
SSL Termination & Certificates
GCP LB handles TLS termination at the edge — the backend receives plain HTTP internally, reducing CPU load. Google-managed SSL certificates auto-provision and auto-renew via Certificate Manager.
Google-managed · Self-managed · Certificate Map

Load Balancing Algorithms

Round Robin
Requests are distributed evenly to each backend in sequence. Simple and predictable.
→ Default for equal-weight backends
Least Connections
Routes to the backend with the fewest active connections. Best for long-lived connections.
→ WebSocket · gRPC streaming
Weighted Round Robin
Backends with higher weights receive proportionally more traffic. Used in canary deploys.
→ Traffic splitting · Canary releases
IP Hash / Sticky
A hash of the client IP determines which backend handles the request consistently.
→ Stateful sessions
Geolocation Routing
Routes client requests to the geographically closest backend region, reducing latency.
→ Multi-region deployments

GCP Load Balancer Types

Type Layer Scope Use Case Protocol
Global External HTTPS LB L7 Global Web apps, APIs — most common choice HTTP, HTTPS, HTTP/2, gRPC
Regional External HTTPS LB L7 Regional Single-region web apps, lower cost HTTP, HTTPS
External TCP/SSL Proxy LB L4 Global Non-HTTP TCP workloads, databases TCP, SSL
External Network LB L4 Regional UDP traffic, pass-through (preserves client IP) TCP, UDP, ESP, ICMP

✦ Key Learnings — Load Balancer
💡GCP's Global LB uses a single Anycast IP — all regions served from one IP address, with routing happening on Google's backbone.
💡Always use L7 (HTTPS) LB for microservices — it enables URL path routing, header inspection, and can integrate directly with Cloud Armor for WAF.
💡Use Serverless NEGs to load-balance directly to Cloud Run or Cloud Functions without managing VMs.
💡Health check intervals should be tuned per service — too short causes flapping, too long causes slow failover. Typical: check every 5s, unhealthy after 2 failures.
💡Connection draining (default 300s) lets in-flight requests complete before a backend is removed — critical for zero-downtime deploys.

& Apigee

GCP offers two products for API management: Cloud API Gateway (lightweight, serverless-focused) and Apigee (enterprise-grade, full lifecycle). Both sit between clients and your backend services, enforcing policies and providing observability.

🗺️
API Routing & Path Matching
The gateway maps incoming URL paths to specific backend services. /api/v1/users/** → User Service, /api/v1/orders/** → Order Service. This decouples the public API surface from internal service URLs.
OpenAPI 3.0 spec-driven routing
🔑
Authentication at the Gateway
API Gateway validates JWT tokens, API keys, or OAuth2 tokens before forwarding requests. This centralizes auth logic — individual microservices don't need to re-validate tokens, they trust the gateway has already done it.
securityDefinitions: jwt · apiKey · oauth2
🚦
Rate Limiting & Quotas
Protect backends from abuse and overload by limiting requests per consumer. GCP API Gateway supports per-API-key quotas, per-consumer rate limits, and burst allowances configurable in the OpenAPI spec or Apigee policies.
x-google-quota: metricCosts · limits
🔄
Request / Response Transformation
Apigee (the enterprise tier) can transform request and response payloads, add/remove headers, convert between JSON and XML, mask PII fields in responses, and inject tracing headers before forwarding to backends.
AssignMessage · JSONToXML · MaskData policies
📊
Observability & Analytics
Every request through the gateway produces logs, metrics, and traces. Cloud Logging captures access logs. Cloud Monitoring tracks latency, error rates, and quota usage. Apigee adds developer portal analytics and API usage dashboards.
Cloud Trace · Logging · Monitoring · Apigee Analytics
🔀
Canary & Version Management
Route a percentage of traffic to a new API version for canary testing. The gateway can split traffic between v1 and v2 backends based on weights, headers, or API key tiers — without changing client code.
Traffic splitting · A/B routing · API versioning

OpenAPI Config Example

// openapi-config.yaml — GCP API Gateway Spec
swagger: "2.0"
info:
  title: My Microservice API
  version: "1.0.0"

schemes: [https]
produces: [application/json]

# Global security — JWT validation on every route
securityDefinitions:
  firebase:
    authorizationUrl: ""
    flow: implicit
    type: oauth2
    x-google-issuer: "https://securetoken.google.com/PROJECT_ID"
    x-google-jwks_uri: "https://www.googleapis.com/service_accounts/v1/jwk/..."

paths:
  /users/{userId}:
    get:
      summary: Get user by ID
      operationId: getUser
      security:
        - firebase: []
      x-google-backend:
        address: https://user-service-abc123-uc.a.run.app
      x-google-quota:
        metricCosts:
          "users-quota": 1

  /orders:
    post:
      summary: Create order
      x-google-backend:
        address: https://order-service-xyz789-uc.a.run.app
        deadline: 30.0  # timeout in seconds
✦ Key Learnings — API Gateway
💡The API Gateway is the single entry point for all clients — it abstracts away the internal service topology. Clients never call services directly.
💡Validate JWTs at the gateway, not in individual services. Services should only receive requests that have already been authenticated, reducing code duplication and attack surface.
💡Cloud API Gateway is best for Cloud Run / serverless. For on-prem / hybrid, use Cloud Endpoints with ESPv2 sidecar. For enterprise with monetization needs, use Apigee.
💡Set explicit backend deadlines in the OpenAPI config to avoid gateway timeouts cascading into backend overload (set deadline slightly less than your backend's own timeout).
💡Use API versioning in the path (/v1/, /v2/) and route different versions to different backends — enables zero-downtime major API upgrades.

Chapter Three

Security
Architecture

GCP provides a layered security model — from the network edge down to individual service identities. Defense-in-depth means each layer independently validates, filters, and authorizes traffic so no single failure exposes your system.

Defense-in-Depth Layers

1
🛡️ Cloud Armor — Edge Protection
GCP's managed Web Application Firewall (WAF) and DDoS protection. Blocks OWASP Top 10 threats (SQLi, XSS), volumetric DDoS attacks, and allows IP allowlist/blocklist rules. Applied before traffic even hits your LB backends.
WAF DDoS
2
🔒 HTTPS / TLS Termination
All traffic from clients to the LB is encrypted with TLS 1.2/1.3. Google-managed certificates auto-renew. Internally, traffic can use HTTP within a private VPC, or you can enforce internal TLS with Certificate Authority Service for full encryption in transit.
TLS 1.3 Managed Cert
3
🚀 API Gateway Auth — JWT / OAuth2 / API Keys
Every request must carry a valid credential. The API Gateway validates JWTs against a known JWKS endpoint (Firebase Auth, Google Identity, or custom IdP), verifies API keys against its registry, and rejects anything that doesn't match.
JWT OAuth2
4
🔐 Identity-Aware Proxy (IAP)
IAP enforces access control based on user identity and context (device posture, location) for internal tools and admin services, without a VPN. It integrates with Google Workspace accounts and supports BeyondCorp enterprise access policies.
BeyondCorp Zero-Trust
5
🎭 IAM — Service Account Permissions
Each microservice runs as a dedicated GCP Service Account with the minimum required IAM roles (principle of least privilege). Services authenticate to GCP APIs using Workload Identity (in GKE) or attached Service Accounts — no long-lived keys.
IAM Workload ID
6
🔗 mTLS — Service-to-Service Auth
Within the cluster/VPC, services authenticate each other using mutual TLS (both sides present certificates). Managed by Istio service mesh or Traffic Director. Ensures a compromised service can't impersonate another, even inside the private network.
mTLS Istio
7
🔑 Secret Manager — Credentials at Rest
Database passwords, API keys, and certificates are stored in GCP Secret Manager (never in code or environment variables). Services fetch secrets at startup via the Secret Manager API, encrypted at rest with Cloud KMS, with full audit logging.
Secrets KMS

Recommended GCP Security Stack

1
Edge Protection
Put Cloud Armor in front of your public Application Load Balancer so malicious traffic is filtered before it reaches APIs or service backends.
Cloud ArmorWAFDDoS
2
API Front Door
Use API Gateway for lightweight managed API control or Apigee when you need deeper policy, governance, developer portals, or monetization.
API GatewayApigeeJWT
3
Service Identity
Run each workload under its own service account with minimum IAM roles. Avoid shared admin identities and avoid distributing long-lived keys.
IAMLeast PrivilegeWorkload Identity
4
Private Service Mesh
Keep east-west traffic private, and add mTLS with Istio or Traffic Director when service-to-service identity and encryption are required.
mTLSIstioPrivate VPC
Key Learnings - Security
1.Security is strongest when it is layered. Cloud Armor, TLS, gateway auth, IAM, network controls, and secret management each address different failure modes.
2.Do authentication and coarse-grained filtering as early as possible. Reject bad traffic before it reaches internal microservices.
3.Least privilege matters for workloads too, not just humans. Every service should have a narrowly scoped service account.
4.Never rely on a private network alone as your trust model. Internal service identity, mTLS, and explicit authorization still matter.
5.Secrets should be managed centrally with rotation and auditability, not embedded in source code, container images, or copied environment files.
