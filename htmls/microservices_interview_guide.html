REST best practices — 15 golden rules
1. Nouns not verbs: /users not /getUsers
2. Plural resources: /orders not /order
3. Correct HTTP methods: GET read · POST create · PUT replace · PATCH update · DELETE remove
4. Correct status codes — never return 200 for errors
5. Version APIs: /api/v1/users
6. Pagination: ?page=1&size=20
7. Sorting/filtering: ?sort=createdAt,desc&status=PAID
8. Consistent JSON response: include success, data, error, timestamp
9. Meaningful error messages with error codes
10. Always HTTPS — never plain HTTP
11. Use Idempotency-Key for POST payments/orders
12. ETag for concurrency: If-Match: "v3"
13. Stateless — each request contains all needed info
14. Document with OpenAPI/Swagger
15. Log with Request-ID and Correlation-ID

Idempotency — payment example
Without idempotency: client retries → ₹5000 charged twice.

Client sends POST + Idempotency-Key: txn-123
→
Check Redis for key
→
Not found → process → store result (TTL 24h)
On retry: key found → return cached response. No duplicate charge.
public <T> T execute(String key, Supplier<T> action) { if (redis.hasKey("idem:" + key)) return redis.get("idem:" + key); T result = action.get(); redis.set("idem:" + key, result, Duration.ofHours(24)); return result; }

Interview Q&A
Top 30 questions with concise answers — test yourself
Architecture & core concepts (Q1–Q10)
Q1. What are microservices vs monolith?
Microservices = small, independent, independently deployable services communicating via APIs. Monolith = single codebase, one deployment. Microservices win on scalability, fault isolation, and agility. Monoliths are simpler for small teams.
Q2. What is service discovery?
Mechanism for services to find each other dynamically without hardcoded IPs. Services register with a registry (Eureka, Consul); others query it. Two types: client-side (client queries registry) and server-side (gateway/LB handles it).
Q3. How do you handle data consistency?
Use eventual consistency via async events. Avoid distributed ACID transactions. Use Saga pattern for distributed workflows. Outbox pattern for guaranteed event publishing.
Q4. What is API Gateway and what does it do?
Single entry point for all client requests. Handles routing, authentication, rate limiting, logging, protocol translation, and response aggregation.
Q5. Sync vs async — when to use what?
Sync (REST, gRPC) for real-time, user-facing, low latency. Async (Kafka, RabbitMQ) for decoupling, high throughput, resilience. Async introduces eventual consistency.
Q6. Database per service — why?
Each service owns its data. Prevents tight coupling, enables independent scaling and tech choice. Cross-service data consistency handled via events/Saga, not shared DB.
Q7. What is eventual consistency?
Data across services will become consistent over time, not instantly. Requires idempotent operations. Acceptable in high-scale systems where strong consistency is too costly.
Q8. What is bounded context?
From DDD — a clear boundary where a service has one responsibility and its own domain model. Prevents overlap and keeps services loosely coupled.
Q9. How do you test microservices?
Unit (logic in isolation), Integration (interactions with DB/other services), Contract (API agreement between services using Pact), End-to-End (full user journey), Performance (Gatling, JMeter).
Q10. What are anti-patterns in microservices?
Shared database (tight coupling), god service (monolith in disguise), chatty APIs (too many sync calls), no monitoring, no API versioning.
Patterns & resilience (Q11–Q20)
Q11. Explain Circuit Breaker.
Prevents cascading failures. States: Closed (normal), Open (blocking all calls after failures), Half-Open (testing recovery). Tool: Resilience4j.
Q12. What is the Saga pattern?
Manages distributed transactions via local transactions + compensating actions on failure. Choreography (event-driven, decentralized) vs Orchestration (central coordinator). Use when you can't use 2PC.
Q13. What is CQRS?
Separate read (Query) and write (Command) models. Write DB triggers events → read model updated async. Scale reads independently. Use for complex domains or read-heavy systems. Overkill for simple CRUD.
Q14. How do you prevent cascade failure?
Circuit breaker + timeouts + fallbacks + bulkheads. Each isolates the failure. Never let one service exhaust all resources.
Q15. What is a Service Mesh?
Infrastructure layer using sidecar proxies (Envoy) per service. Handles mTLS, traffic management (canary, retries), observability — without changing application code. Tools: Istio, Linkerd.
Q16. Choreography vs Orchestration?
Choreography = services react to events (decentralized, loose). Orchestration = central controller tells services what to do (easier to trace, tighter coupling). Use choreography for simple, orchestration for complex workflows.
Q17. How handle transactions in microservices?
Avoid distributed ACID. Use Saga pattern. Each service has local transaction; compensate on failure. Use event-driven approach via Kafka/RabbitMQ.
Q18. API Gateway vs Load Balancer?
API Gateway = smart entry point (auth, routing, rate limiting, aggregation). Load Balancer = traffic distributor across instances of one service. Use Gateway at the perimeter, LB internally.
Q19. What is distributed tracing?
Track requests across services via Trace ID + Span IDs in headers. Zipkin/Jaeger visualizes the full timeline. Spring Boot 3 uses Micrometer Tracing.
Q20. What is idempotency and why does it matter?
Same operation multiple times = same result. Critical for retries. Use Idempotency-Key header for POST. Store key + response in Redis (24h TTL). Prevents duplicate payments, orders.
Security, deploy & config (Q21–Q30)
Q21. How do you secure microservices?
JWT/OAuth2 at gateway, mTLS between services, RBAC authorization, HTTPS always, Vault for secrets, rate limiting, network policies via service mesh.
Q22. JWT vs Session auth?
JWT = stateless (server stores nothing), scalable, short-lived. Session = server stores state (memory/Redis), requires sticky sessions or shared session store. JWT preferred for microservices.
Q23. How do you handle config management?
Spring Cloud Config / Consul for centralized config. Kubernetes ConfigMaps and Secrets. Vault for sensitive data. Dynamic refresh via Actuator bus-refresh without redeployment.
Q24. How do you version APIs?
URL versioning (/api/v1/users) is simplest and most visible. Also: header versioning (Accept-Version: v1) or media type versioning. Maintain backward compatibility — never break existing clients.
Q25. How do you monitor microservices?
Logging = ELK Stack. Metrics = Prometheus + Grafana. Tracing = Zipkin/Jaeger. Health checks via Spring Actuator. Alerts via PagerDuty or SNS. Correlation IDs tie everything together.
Q26. What is blue-green deployment?
Two identical environments (Blue=live, Green=new). Deploy to Green, test, then switch traffic. Rollback = switch back to Blue instantly. Zero downtime.
Q27. What does Kubernetes provide?
Container orchestration: scheduling, horizontal scaling, self-healing, service discovery, rolling deploys, load balancing, config/secret management.
Q28. What is the Strangler Fig pattern?
Migrate monolith to microservices incrementally. Route some traffic to new service, rest to monolith. Gradually increase until monolith is fully replaced. No big-bang rewrite.
Q29. What is the role of CI/CD in microservices?
Automates build, test, deploy per service. Enables independent deployment. Supports zero-downtime releases, automated rollback, environment promotion.
Q30. Kafka consumer slower than producer?
Backpressure / consumer lag. Fix: increase partitions (more parallelism), batch processing, async processing, pause/resume on lag, dead-letter queue for failed messages, monitor with consumer group lag alerts.
