GCP Traffic Management

Load Balancer

A load balancer is the public traffic director for your system. In GCP it terminates client traffic, applies edge policies, checks backend health, and sends requests to the best available service instance.

Main job Distribute traffic without making clients care where services actually run.
Typical GCP choice Global external Application Load Balancer for HTTP and HTTPS microservice traffic.
Why it matters It improves availability, rollout safety, latency, and edge security in one place.
Request Path

How traffic moves through the edge

1. Client

Browser, mobile app, or another service sends HTTPS traffic to one public endpoint.

2. Frontend

GCP load balancer terminates TLS, accepts the request, and applies URL or host rules.

3. Edge policy

Cloud Armor can inspect the request before it reaches your backends.

4. Backend service

The request is sent to a healthy backend target such as GKE, MIG, or Cloud Run via NEG.

5. Response

The backend responds, and the same edge layer exposes a stable endpoint to the client.

Client -> TLS termination -> policy checks -> healthy backend -> response
Core Concepts

What you should understand

Global anycast IP

Clients hit one public IP, and Google routes them to the nearest healthy edge location. That reduces latency and hides regional backend complexity.

Layer 7 routing

Application load balancers can route by host, path, and header. That is how one endpoint can send /users and /orders to different services.

Health checks

GCP continuously probes backends. Unhealthy instances are removed from the serving pool automatically so bad nodes stop receiving traffic.

Connection draining

When a backend is removed during deploy or autoscaling, in-flight requests can finish instead of being cut off mid-request.

Autoscaling compatibility

The load balancer works best when the backend pool can grow or shrink independently. That makes it a natural match for GKE, MIGs, and Cloud Run.

GCP Mapping

Services you usually combine

Application Load Balancer

Primary choice for HTTP and HTTPS traffic. Best when you want host and path routing, TLS offload, and global edge entry.

Cloud Armor

Add WAF and DDoS protection at the edge. Commonly paired with the load balancer, not buried inside each microservice.

Serverless NEG

Connect Cloud Run or other serverless backends behind the load balancer without exposing them directly.

Managed SSL certificates

Use Google-managed certs to avoid manual certificate rotation on each service.

Backend services + health checks

These are the units where you define instance groups or NEGs, balancing behavior, and liveness checks.

Key Learnings

Interview-ready takeaways

Load balancer and API gateway are not the same thing.

The load balancer focuses on traffic distribution and edge routing. The gateway focuses on API policy, auth, quotas, and API contract management.

Health checks are a reliability control, not a checkbox.

Poor health-check timing can either flap healthy nodes or fail too slowly during incidents.

Use the edge for cross-cutting concerns.

TLS termination, DDoS protection, and request filtering belong at the entry layer so every service benefits from the same protection.

Plan for rollout safety.

Connection draining and staged backend changes matter during deploys just as much as normal traffic balancing.

Keep backend services private when possible.

Expose one controlled entry path and reduce the number of public surfaces clients can hit directly.
