01 OAuth2 + OIDC + JWT Flow Recommended for modern apps
Real-world examples

What OAuth2 does

Defines the process of getting a token — the flows (Auth Code, Client Credentials, etc.) and handshakes between parties. It does NOT define token format.

What OIDC adds

Sits on top of OAuth2. Adds identity — tells your app who the user is via an ID Token. Without OIDC, OAuth2 only tells you what the app can access.

Key insight: Spring Boot's resource server never contacts the Auth Server per request. It verifies the JWT signature using the /.well-known/jwks.json public keys — downloaded once, cached. Fully stateless.

ADFS = Active Directory Federation Services — Microsoft's on-premise identity provider. An employee on the Windows corporate network opens an internal app. ADFS intercepts the request, shows the Windows login page, authenticates against Active Directory (LDAP), and issues a token. The employee never has a separate app username/password — they use their Windows credentials.

JWT path (modern ADFS)

ADFS 4.0+ (Server 2016+) supports OIDC. Spring Boot configures a standard JwtDecoder pointing at the ADFS OIDC endpoint. Works exactly like any OAuth2 IdP.

SAML path (legacy ADFS)

Older setups issue SAML assertions. Spring Security SAML extension (or Spring Security 6 SAML2) parses the XML assertion and maps claims to Authentication. Heavier but required for legacy.

ADFS vs Azure AD (Entra ID): ADFS is the on-premise version. Azure AD / Entra ID is the cloud version. Same concepts, but Azure AD is easier (managed, auto-scales) and Microsoft recommends it for new projects.
03 LDAP + IdP Architecture Directory-backed identity
Real-world examples
University SSO (OpenLDAP + Keycloak) On-premise enterprise with Keycloak Linux sysadmin portal (389 Directory Server)

LDAP (Lightweight Directory Access Protocol) is a protocol for reading a directory of users and groups (like a phone book for IT). OpenLDAP and Active Directory both speak LDAP. The key architectural rule: Spring Boot NEVER talks to LDAP directly. An IdP like Keycloak federates with LDAP, translates groups into JWT roles, and Spring Boot only ever sees a JWT.

Why not query LDAP directly from Spring?

  • Tight coupling — LDAP schema changes break app
  • LDAP connection pool per request = slow
  • No SSO across multiple apps
  • JWT is stateless; LDAP is stateful

CORS — Cross-Origin Resource Sharing

CORS is a browser security feature. It does nothing on the server — the browser blocks the response from reaching JavaScript if the server doesn't include the right headers. Direct API calls (curl, Postman) ignore CORS entirely.

Same-Origin (no CORS needed)

Frontend: https://myapp.com Backend: https://myapp.com/api // Same protocol + domain + port // Browser allows freely // Cookies work automatically

Cross-Origin (CORS required)

Frontend: https://app.client.com ← different domain Backend: https://api.server.com // Browser sends preflight OPTIONS // Server must respond with headers: Access-Control-Allow-Origin: https://app.client.com Access-Control-Allow-Credentials: true Access-Control-Allow-Methods: GET, POST, PUT Access-Control-Allow-Headers: Content-Type, X-XSRF-TOKEN

Common CORS mistakes

  • Allow-Origin: * + credentials — browser blocks this combination (spec forbids it)
  • Wildcard * in production — any site can make requests to your API
  • Skipping preflight response — browser will block the actual request
  • Exposing all headers — only expose what frontend actually needs
@Configuration public class CorsConfig { @Bean public CorsConfigurationSource source() { CorsConfiguration cfg = new CorsConfiguration(); cfg.setAllowedOrigins(List.of( "https://app.client.com" )); cfg.setAllowedMethods(List.of("GET","POST","PUT")); cfg.setAllowCredentials(true); // for cookies cfg.setExposedHeaders(List.of("X-XSRF-TOKEN")); ... } }
CSRF — Cross-Site Request Forgery

CSRF exploits the fact that browsers automatically attach cookies to every request to a domain, even if the request originates from a different site.

The CSRF attack scenario

  1. Alice logs into bank.com — session cookie stored
  2. Alice visits evil.com (same browser)
  3. evil.com has hidden form: POST bank.com/transfer?to=attacker&amount=1000
  4. Browser auto-attaches Alice's bank.com cookie
  5. Bank sees valid session — transfer executes
Alice never clicked anything on bank.com. The cookie did it.

Spring Boot CSRF protection (Synchronizer Token Pattern)

// 1. Spring generates CSRF token Set-Cookie: XSRF-TOKEN=abc123; SameSite=Lax // (readable by JS — not HttpOnly) // 2. Angular reads cookie, sends as header X-XSRF-TOKEN: abc123 // 3. Spring validates header == cookie value // evil.com cannot read the cookie (SameSite) // so cannot forge the header
The double-submit cookie pattern: attacker can make the browser send the cookie, but cannot read it to forge the header.

When CSRF protection is NOT needed

  • Stateless JWT in Authorization: Bearer header — JS must explicitly set this header; browsers don't auto-attach it
  • API-only backend with no browser clients
  • SameSite=Strict cookies (no cross-site request will ever carry the cookie)

08 JWT vs OAuth2 — What Each One Actually Is

JWT — a token format

JWT is just a data container — a signed JSON object. It carries claims about a user. It has nothing to say about how you got it.

  • Self-contained — no DB lookup to validate
  • Signed (RS256 or HS256) — tamper-proof
  • Can be used standalone, with OAuth2, or with SAML
  • Expires via exp claim
  • Analogy: A signed boarding pass — it carries info, you just verify the signature

OAuth2 — an authorization protocol

OAuth2 defines the process of obtaining a token — the multi-party dance between User, Client, Auth Server, and Resource Server.

  • Defines flows: Auth Code, Client Credentials, Implicit, Device
  • Does NOT define token format (but usually issues JWT)
  • Separates: who grants access vs who verifies it
  • OIDC layer adds identity (ID Token = who the user is)
  • Analogy: The airport boarding process — it's how you get the boarding pass
Used together: OAuth2 defines the flow → Auth server issues a JWT → Spring Boot validates the JWT. You need both: OAuth2 for the secure issuance process, JWT for efficient stateless verification.
# application.yml — Spring Boot as a Resource Server spring: security: oauth2: resourceserver: jwt: issuer-uri: https://auth.corp.com # OAuth2/OIDC discovery jwk-set-uri: https://auth.corp.com/jwks # fetch public keys to verify JWT # Spring Boot fetches jwks.json once, caches public keys # Every request: decode JWT → verify signature → check exp/iss/aud → done # Zero database calls
