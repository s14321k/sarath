Basic Login Flow (Username/Password)

The simplest authentication mechanism where users submit credentials directly to the server. After validation, the server typically creates a session.

┌─────────┐ ┌─────────┐ │ Browser │ │ Server │ └────┬────┘ └────┬────┘ │ │ │ 1. User enters credentials │ │ (username + password) │ │ │ │────────────────────────────────────▶ │ │ POST /login │ │ {user: "john", pass: "***"} │ │ │ │ 2. Validate │ credentials │ against DB │ │ │ 3. Create │ session & │ session ID │ │ │ ◀──────────────────────────────────── │ │ Set-Cookie: sessionId=abc123 │ │ Redirect to /dashboard │ │ │ │ 4. Subsequent requests include cookie │ │ ────────────────────────────────────▶ │ │ Cookie: sessionId=abc123 │ │ │ │ 5. Verify │ session │ │ │ ◀──────────────────────────────────── │ │ 200 OK + Protected Resource │ └────────────────────────────────────────┘

Key Points:

  • Credentials sent over HTTPS (must be encrypted)
  • Server creates and maintains session state
  • Session ID stored in cookie
  • Stateful - server must remember sessions

Session-Based Authentication (Detailed)

Shows the complete lifecycle of a session including creation, validation, and logout.

┌─────────┐ ┌─────────┐ ┌──────────┐ │ Browser │ │ Server │ │ Database │ └────┬────┘ └────┬────┘ └────┬─────┘ │ │ │ │ LOGIN │ │ │───────────────▶│ │ │ │───────────────▶│ │ │ Check user/pass │ │ │◀───────────────│ │ │ ✓ Valid │ │ │ │ │ │───────────────▶│ │ │ Store session │ │ │ ID: xyz789 │ │◀───────────────│ User: john │ │ Cookie: xyz789 │ Expires: 1hr │ │ │ │ │ ACCESS RESOURCE│ │ │───────────────▶│ │ │ Cookie: xyz789 │ │ │ │───────────────▶│ │ │ Validate session│ │ │◀───────────────│ │ │ ✓ Valid │ │◀───────────────│ │ │ 200 OK │ │ │ + Data │ │ │ │ │ │ LOGOUT │ │ │───────────────▶│ │ │ │───────────────▶│ │ │ Delete session │ │◀───────────────│ │ │ Clear cookie │ │ └ └ ┘

Key Points:

  • Server stores session data (in memory, Redis, or database)
  • Cookie contains only session ID, not user data
  • Sessions can expire based on time or inactivity
  • Logout destroys server-side session

OAuth 2.0 (Authorization Code Flow)

OAuth 2.0 is an authorization framework that enables a third-party application to obtain limited access to a user's resources without exposing credentials. Example: "Sign in with Google"

┌─────────┐ ┌─────────────┐ ┌──────────────┐ ┌──────────────┐ │ User │ │ Client App │ │ Auth Server │ │Resource Srv │ │(Browser)│ │(Your Site) │ │ (Google) │ │(Google API) │ └────┬────┘ └──────┬──────┘ └──────┬───────┘ └──────┬───────┘ │ │ │ │ │ 1. Click │ │ │ │ "Sign in │ │ │ │ w/ Google" │ │ │ │──────────▶│ │ │ │ │ │ │ │ │ 2. Redirect to auth │ │ │◀──────────│─────────────▶│ │ │ client_id=123 │ │ │ redirect_uri=mysite.com/callback │ │ scope=profile email │ │ │ │ │ │ 3. User logs in & approves │ │ │───────────────────────────▶│ │ │ (username/password) │ │ │ │ │ │ 4. Redirect back with code │ │ │◀───────────────────────────│ │ │ mysite.com/callback?code=AUTH_CODE │ │ │ │ │ │──────────▶│ │ │ │ (browser │ │ │ │ follows) │ │ │ │ │ │ │ │ │ 5. Exchange code for token │ │ │─────────────▶│ │ │ │ code=AUTH_CODE │ │ │ client_secret=│ │ │ │◀─────────────│ │ │ │ access_token │ │ │ │ refresh_token│ │ │ │ │ │ │ │ 6. Use token to access resources │ │ │─────────────────────────────────▶│ │ │ Authorization: Bearer ACCESS_TOKEN │ │◀─────────────────────────────────│ │ │ User profile data │ │ │ │ │ │◀──────────│ │ │ │ Logged in! │ │ │ └ └ └ ┘

Key Points:

  • Authorization Code: Temporary, single-use code
  • Access Token: Used to access protected resources
  • Refresh Token: Used to get new access tokens
  • Client secret never exposed to browser
  • User never shares password with your app

Security Features:

  • PKCE (Proof Key for Code Exchange) for public clients
  • State parameter prevents CSRF attacks
  • Short-lived access tokens
  • Scopes limit what app can access

OpenID Connect (OIDC)

OpenID Connect is an identity layer built on top of OAuth 2.0. While OAuth 2.0 is for authorization (granting access), OIDC is for authentication (verifying identity). It adds an ID Token with user information.

┌─────────┐ ┌─────────────┐ ┌──────────────┐ │ User │ │ Client App │ │OpenID Provider│ │(Browser)│ │ │ │ (Okta) │ └────┬────┘ └──────┬──────┘ └──────┬───────┘ │ │ │ │ 1. Initiate login │ │──────────▶│ │ │ │ │ │ │ 2. Redirect with OpenID scope │◀──────────│─────────────▶│ │ scope=openid profile email │ response_type=code │ │ client_id=... │ │ │ │ 3. Authenticate │ │───────────────────────────▶│ │ Login page │ │ (username/password) │ │ │ │ 4. Consent screen │ │◀───────────────────────────│ │ "Allow access to │ │ your profile?" │ │ │ │───────────────────────────▶│ │ User approves │ │ │ │ 5. Redirect with code │ │◀───────────────────────────│ │ ?code=XYZ123 │ │ │ │ │──────────▶│ │ │ │ │ │ │ 6. Exchange for tokens │ │─────────────▶│ │ │ POST /token │ │ │ code=XYZ123 │ │ │ │ │ │◀─────────────│ │ │ access_token │ │ │ id_token (JWT)│ │ │ refresh_token│ │ │ │ │ │ 7. Decode ID Token │ │ Header: │ │ │ alg, kid │ │ │ Payload: │ │ │ sub: user123 │ │ │ name: John │ │ │ email: j@ex │ │ │ iat, exp │ │ │ │ │◀──────────│ │ │ Welcome, │ │ │ John! │ │ └ └ ┘

OAuth 2.0 vs OpenID Connect:

  • OAuth 2.0: "What can this app do?" (authorization)
  • OIDC: "Who is this user?" (authentication)
  • ID Token: JWT containing user identity claims
  • UserInfo Endpoint: Additional user profile data

ID Token (JWT) Structure:

{
  "sub": "user_id_12345",      // Subject (user identifier)
  "name": "John Doe",
  "email": "john@example.com",
  "iss": "https://auth.example.com",  // Issuer
  "aud": "your_client_id",     // Audience
  "iat": 1638360000,           // Issued at
  "exp": 1638363600            // Expiration
}

Single Sign-On (SSO) with SAML

SSO allows users to log in once and access multiple applications. SAML (Security Assertion Markup Language) is an XML-based protocol commonly used in enterprise environments.

┌─────────┐ ┌─────────────┐ ┌──────────────┐ │ User │ │Service Provdr│ │Identity Provdr│ │(Browser)│ │ (SP/App) │ │ (IdP/Okta) │ └────┬────┘ └──────┬──────┘ └──────┬───────┘ │ │ │ │ 1. Access protected resource │──────────▶│ │ │ app.com/ │ │ │ dashboard │ │ │ │ │ │ │ 2. No session found │ │ Generate │ │ │ SAML Request│ │ │ │ │◀──────────│ │ │ 302 Redirect to IdP │ │ + SAML Request (base64) │ │ │ │ 3. Forward to IdP │ │───────────────────────────▶│ │ SAML Request │ │ <AuthnRequest> │ │ │ │ 4. IdP checks for existing session │ If none, show login │ │◀───────────────────────────│ │ Login page │ │ │ │ 5. User authenticates │ │───────────────────────────▶│ │ username + password │ │ │ │ 6. IdP creates session │ │ Generates SAML Response│ │ <Assertion> │ │ Subject: john@company │ │ Attributes: name, email│ │ Signed with IdP cert │ │ │ │◀───────────────────────────│ │ 302 Redirect to SP │ │ + SAML Response │ │ │ │ 7. Browser submits to SP │ │──────────▶│ │ │ POST │ │ │ SAMLResponse │ │ │ │ │ │ 8. Validate signature │ │ Extract user info │ │ Create local session │ │ │ │◀──────────│ │ │ Set cookie│ │ │ Show dashboard │ │ │ │ │ 9. Access another app (app2.com) │─────────────────────────▶ │ │ │ │ 302 to IdP │ │◀───────────────────────────│ │ 10. IdP has existing session! │ No login needed │ │───────────────────────────▶│ │ │ │◀───────────────────────────│ │ SAML Response for app2 │ │ │ │ │ 11. Logged into app2! │ └ └ ┘

SSO Benefits:

  • Login once, access multiple apps
  • Centralized user management
  • Consistent security policies
  • Better user experience

SAML Security:

  • Assertions are digitally signed
  • XML encryption for sensitive data
  • Time-limited assertions
  • Certificate-based trust between IdP and SP

CSRF (Cross-Site Request Forgery) Protection

CSRF is an attack where a malicious site tricks your browser into making unwanted requests to a site where you're authenticated. CSRF tokens prevent this.

WITHOUT CSRF PROTECTION (Vulnerable): ┌─────────┐ ┌──────────┐ ┌─────────────┐ │ User │ │ Evil Site│ │ Legit Bank │ └────┬────┘ └────┬─────┘ └──────┬──────┘ │ │ │ │ 1. User logged into bank │──────────────────────────▶│ │ Cookie: session=abc123 │ │ │ │ │ 2. User visits evil site │ │─────────▶│ │ │ │ │ │ │ 3. Evil page contains: │ │ <form action="bank.com/transfer"> │ │ <input name="to" value="hacker"> │ │ <input name="amount" value="1000"> │ │ </form> │ │ <script> │ │ document.forms[0].submit(); │ │ </script> │ │ │ │ 4. Browser auto-submits form │──────────────────────────▶│ │ Cookie: session=abc123 │ │ to=hacker, amount=1000 │ │ │ │ │ │ 5. ❌ Request │ │ succeeds! │ │ Money transferred │◀──────────────────────────│ │ 200 OK │ └ └ ┘ WITH CSRF PROTECTION (Secure): ┌─────────┐ ┌─────────────┐ │ User │ │ Legit Bank │ └────┬────┘ └──────┬──────┘ │ │ │ 1. Load transfer form │ │────────────────────────▶│ │ │ │ 2. Generate │ CSRF token │ csrf=xyz789 │ Store in session │ │ │◀────────────────────────│ │ Form HTML: │ │ <input type="hidden" │ │ name="csrf_token" │ │ value="xyz789"> │ │ │ │ 3. User submits form │ │────────────────────────▶│ │ Cookie: session=abc123 │ │ csrf_token=xyz789 │ │ to=friend, amount=100 │ │ │ │ 4. Validate: │ - Session exists? ✓ │ - CSRF token matches? ✓ │ │ │◀────────────────────────│ │ ✓ Transfer successful │ │ │ │ ATTACK SCENARIO: │ │ User on evil site │ │ Evil form submits │ │────────────────────────▶│ │ Cookie: session=abc123 │ │ ❌ NO csrf_token! │ │ │ │ 5. Reject: │ CSRF token missing │◀────────────────────────│ │ 403 Forbidden │ └ ┘

How CSRF Tokens Work:

  • Server generates unique token per session/request
  • Token included in forms as hidden field
  • Server validates token on submission
  • Evil sites can't access the token (Same-Origin Policy)

Additional CSRF Protections:

  • SameSite Cookies: Cookie only sent on same-site requests
  • Double Submit Cookie: Token in both cookie and form
  • Custom Headers: X-Requested-With for AJAX
  • Origin/Referer Validation: Check request source

LDAP (Lightweight Directory Access Protocol)

LDAP is a protocol for accessing and maintaining directory services. Commonly used in enterprises for centralized authentication against Active Directory or similar directory servers.

┌─────────┐ ┌─────────────┐ ┌──────────────┐ │ User │ │Application │ │ LDAP Server │ │(Browser)│ │ Server │ │(Active Dir) │ └────┬────┘ └──────┬──────┘ └──────┬───────┘ │ │ │ │ 1. User attempts login │ │──────────▶│ │ │ username: │ │ │ john │ │ │ password: │ │ │ secret123 │ │ │ │ │ │ │ 2. LDAP Bind Request │ │ (Authenticate)│ │ │─────────────▶│ │ │ DN: cn=john, │ │ │ ou=users, │ │ │ dc=company│ │ │ Password: │ │ │ secret123 │ │ │ │ │ │ 3. Verify │ │ credentials │ │ in directory │ │ │ │ │◀─────────────│ │ │ ✓ Bind Success │ │ │ │ │ 4. Search Request │ │ (Get user attributes) │ │─────────────▶│ │ │ Base DN: │ │ │ ou=users, │ │ │ dc=company │ │ │ Filter: │ │ │ (uid=john) │ │ │ Attributes: │ │ │ mail,cn, │ │ │ memberOf │ │ │ │ │ │ 5. Query │ │ directory │ │ │ │ │◀─────────────│ │ │ Search Result│ │ │ DN: cn=John │ │ │ Doe,... │ │ │ mail: j@ex.com │ │ cn: John Doe │ │ │ memberOf: │ │ │ cn=Admins, │ │ │ cn=DevTeam │ │ │ │ │ │ 6. Check group │ │ membership │ │ │ for authorization │ │ Create session │ │ │ │◀──────────│ │ │ ✓ Login │ │ │ successful│ │ │ + Session │ │ │ cookie │ │ └ └ ┘

LDAP Concepts:

  • DN (Distinguished Name): Unique identifier: cn=John,ou=Users,dc=company,dc=com
  • Bind: Authenticate to LDAP server
  • Search: Query directory for entries
  • Attributes: Properties like email, phone, groups
  • Groups: Used for role-based access control

LDAP Security Best Practices:

  • Use LDAPS (LDAP over SSL/TLS) on port 636
  • Use service account with minimal permissions
  • Implement account lockout policies
  • Don't store passwords in app - verify via LDAP bind
  • Cache group memberships to reduce LDAP queries
LDAP Directory Structure Example: dc=company,dc=com │ ├── ou=Users │ ├── cn=John Doe │ │ ├── uid: john │ │ ├── mail: john@company.com │ │ ├── telephoneNumber: 555-1234 │ │ └── memberOf: cn=Admins,ou=Groups,dc=company,dc=com │ │ │ └── cn=Jane Smith │ ├── uid: jane │ └── mail: jane@company.com │ └── ou=Groups ├── cn=Admins │ └── member: cn=John Doe,ou=Users,dc=company,dc=com │ └── cn=DevTeam └── member: cn=Jane Smith,ou=Users,dc=company,dc=com

Authorization in API Gateway

An API Gateway acts as the single entry point for all client requests. It centralizes authentication and authorization so downstream microservices don't each have to implement their own — they trust the gateway to verify identity and pass along claims.

┌──────────┐ ┌─────────────┐ ┌──────────────┐ ┌───────────────┐ │ Client │ │ API Gateway │ │ Auth Server │ │ Microservice │ │(Browser/ │ │(Kong/NGINX/ │ │(Keycloak/ │ │(Order/User/ │ │ Mobile) │ │ AWS GW) │ │ Auth0/Okta) │ │ Payment Svc) │ └────┬─────┘ └──────┬──────┘ └──────┬───────┘ └───────┬───────┘ │ │ │ │ │ STEP 1: CLIENT OBTAINS JWT TOKEN │ │──────────────────────────────▶│ │ │ POST /auth/token │ │ │ { user: "john", │ │ │ password: "***" } │ │ │ │ │ │ │ │─────────────▶│ │ │ │ Validate user│ │ │ │◀─────────────│ │ │ │ access_token │ │ │ │ refresh_token│ │ │◀─────────────────────────────│ │ │ JWT: eyJhbGci...header.payload.sig │ │ │ │ │ │ STEP 2: CLIENT CALLS API WITH TOKEN │ │─────────────▶│ │ │ │ GET /orders │ │ │ │ Authorization: Bearer eyJhbGci... │ │ │ │ │ │ │ STEP 3: GATEWAY VALIDATES TOKEN │ │ │ ┌─────────────────────────────┐│ │ │ │ a) Check token signature ││ │ │ │ (using public key / JWKS) ││ │ │ │ b) Validate expiry (exp) ││ │ │ │ c) Validate issuer (iss) ││ │ │ │ d) Validate audience (aud) ││ │ │ │ e) Extract scopes/roles ││ │ │ └─────────────────────────────┘│ │ │ │ │ │ │ STEP 4: RATE LIMITING & POLICY CHECKS │ │ ┌─────────────────────────────┐│ │ │ │ - Rate limit: 1000 req/min ││ │ │ │ - IP whitelist check ││ │ │ │ - Scope check: "orders:read" ││ │ │ │ - Route permission check ││ │ │ └─────────────────────────────┘│ │ │ │ │ │ │ STEP 5: FORWARD WITH USER CONTEXT │ │──────────────────────────────▶│ │ │ GET /orders │ │ │ │ X-User-Id: user_123 │ │ │ X-User-Role: admin │ │ │ X-User-Email: john@ex.com │ │ │ X-Scope: orders:read │ │ │ (JWT stripped, no raw token │ │ │ passed downstream) │ │ │ │ │ │ │ │ STEP 6: │ │ │ Microservice │ │ │ trusts headers │ │ │ No auth needed! │ │ │ Fetches orders │ │ │ for user_123 │ │◀──────────────────────────────│ │ │ 200 OK │ │ │ │ { orders: [..] } │ │◀─────────────│ │ │ │ 200 OK │ │ │ │ { orders } │ │ │ └ └ └ ┘ REJECTED REQUEST (missing / invalid token): ┌──────────┐ ┌─────────────┐ │ Client │ │ API Gateway │ └────┬─────┘ └──────┬──────┘ │ │ │─────────────▶│ │ GET /orders │ │ ❌ No token │ │ │ │ │ Token missing / expired / │ │ invalid signature detected │◀─────────────│ │ 401 Unauthorized │ { "error": "invalid_token" } └ └ RATE LIMIT / SCOPE VIOLATION: ┌──────────┐ ┌─────────────┐ │ Client │ │ API Gateway │ └────┬─────┘ └──────┬──────┘ │ │ │─────────────▶│ │ DELETE /orders │ scope: "orders:read" │ │ ❌ Scope "orders:delete" │ │ not present in token │◀─────────────│ │ 403 Forbidden │ { "error": "insufficient_scope" } └ └

What the API Gateway Handles:

  • Authentication: Validates JWT signature, expiry, issuer, audience
  • Authorization: Checks scopes/roles against the requested route
  • Rate Limiting: Caps requests per user/IP per window
  • Header Injection: Strips raw token, injects trusted X-User-* headers
  • Routing: Routes to the correct upstream microservice
  • Logging & Tracing: Centralized access logs, correlation IDs

JWKS — How the Gateway Validates JWT Without the Auth Server:

1. Auth Server publishes public keys at:
   GET https://auth.example.com/.well-known/jwks.json
   → { keys: [{ kid, n, e, alg }] }

2. API Gateway fetches & caches these keys

3. On each request:
   - Decode JWT header → get kid (key ID)
   - Find matching public key in JWKS cache
   - Verify token signature locally (no round-trip!)
   - If signature valid → token is authentic

4. Gateway refreshes JWKS cache periodically
   (handles key rotation transparently)

Authentication & Authorization in Microservices

In a microservices architecture, auth is split across multiple layers: the API Gateway handles the perimeter, services communicate internally via service-to-service tokens, and fine-grained authorization (RBAC/ABAC) happens inside each service.

Authorization Models Inside Each Service:

  • RBAC (Role-Based): User has role ADMIN → can DELETE. Role USER → can only READ. Roles extracted from JWT claims.
  • ABAC (Attribute-Based): Decision based on user attributes + resource attributes + environment. E.g. "user.department == resource.owner AND time is business hours"
  • Policy as Code (OPA): Open Policy Agent evaluates Rego policies centrally — services call OPA to ask "can user X do action Y on resource Z?"
  • Resource Ownership: Service checks if userId in token matches the resource owner before allowing mutation.
